# japanese-verbatim

海外の発信（X投稿・講演動画・Web記事）を、**加筆や意訳を排した日本語マークダウン**に変換する Claude Code スキル。

Claude Code を使っていて、英語の技術発信を腰を据えて読みたい人向け。

## なぜ作ったか

海外ユーザーが発信している内容を理解したかった。

X や Web の投稿はブラウザの翻訳機能で読める。しかし動画は難しい。自動字幕は技術用語を取り違えるうえ、再生を止めながら読み進めることになり、腰を据えて向き合わないと内容が入ってこない。

マークダウンにしておけば、時間のあるときに少しずつ読める。検索もできるし、後から参照もできる。これが出発点になっている。

ただし、それだけなら単なる翻訳で終わる。訳しただけの文書は、前提の知識がないと結局わからない。そこで**各ブロックに訳者（Claude）の補足を足す**構成にした。ここがこのスキルの中心にある。

## 特長

### 1. 原文訳と補足を分けて、両方を残す

各セクションを三層構成にして、ブロックの役割を混ぜない。

| ブロック | 内容 | 文体 |
|---|---|---|
| **原文訳** | ソースの内容の日本語化。加筆・意訳をしない | 敬体（です・ます） |
| **画面 / 原文ブロック** | 画面表示・コード・設定。原語のまま残す | — |
| **📝 補足** | 訳者による背景説明。原文に含まれないことを明示 | 常体（である） |

原文が何を言ったのかと、それを理解するために何が要るのかを、読者が区別できる形にしておく。文体を分けているのも、原文の声と訳者の声を見分けるため。

抽出しただけの要約なら、このスキルを通す必要がない。

### 2. 動画の画面をマークダウンに取り込む

スクリーンキャストでは、音声で曖昧だった技術用語はほぼ必ず画面に映っている。設定ファイル、コマンド、ツールの出力。これを該当時刻のフレームとして切り出し、本文に貼る。

- シーン変化を検出して候補を出す（`grab_frames.py`）
- **候補をそのまま貼らない。** 中身を読んで採用する画面を決め、時刻を指定して抜き直す
- 焼き込み字幕は下端、話者のワイプ（小窓）は右端に出るので、切り取ってから貼る

シーン検出が返すのは「画面が切り替わった瞬間」であって、話者がその画面を説明している時刻ではない。前後にずれるため、自動で拾ったものを機械的に並べると図と説明が食い違う。だから2段階にしてある。

### 3. 文字起こしの品質ゲート

**自動文字起こしは静かに内容を落とす。** 落ちたことに気づかないまま整形すると、見た目の整った不完全な文書ができあがる。だから文書を書く前に検査を通す。

音声の欠落は、ギャップの存在ではなく音量の実測を根拠に判定する（無音なのか、発話が消えたのか）。実測した失敗の記録と対処は [`references/asr-playbook.md`](references/asr-playbook.md) にある。

成果物側も、三層構成・忠実性・文体の3つのゲートで検査する（→[4つのゲート](#4つのゲート)）。

### 4. 詳細版と要点版を作り分けられる

長い素材では、深さの違う版を使い分けたくなる。

| 版 | 中身 | 向いている場面 |
|---|---|---|
| **詳細版** | 全節を網羅する。原文の図をそのまま貼り、要所は引用と訳を並べる。各節に📝補足 | 手元で参照し続けるもの |
| **要点版** | 主張だけを短くまとめる。図は要点に関わるものだけ | 通読して全体像を掴むもの |

着手前にどれを作るかを確認する。両方でもよい。後から片方を足すこともできる。

### 5. 訳者の図と原文の図を混ぜない

**原文の図は元画像を貼る。訳者が足す図は Mermaid で描く。**

原文の図を Mermaid で描き直すと情報が落ちる。罫線文字（`┌ ─ │ └`）で画像を再現するのはさらに悪く、原文より分かりにくくなる。Mermaid を使うのは、原文に存在しない図を訳者が足すときだけ。

## 著作権について

**このリポジトリが公開しているのは、変換の手順・スクリプト・用語辞書だけ。生成物は含まれていない。**

このスキルが生成する訳文・文字起こし・取り込んだ出典画像は、いずれも原著作物の二次的著作物にあたる（著作権法27条）。**全文を訳したものは公開できない。** 引用（32条）が求める主従関係を満たさないため。私的使用（30条）の範囲であれば、手元に置いておける。

### 利用者の責任

**このスキルで生成した文書を公開する場合、権利処理は利用者自身の責任で行うこと。**

- 引用の要件（主従関係・明瞭区別・必然性・出所明示）を満たさない全文訳は公開できない
- 動画から切り出した画面も、原著作物の複製にあたる
- 有料講義・有料記事の内容は、私的使用の範囲でも扱いに注意が要る

### スキル側の手当て

このスキル自体も、生成物が混ざらない構成にしてある。

- **全文版を作らない。** 原文の地の文を一文ずつ置き換えた訳は、読者にとって原文の代わりになってしまう。残すのは事実・手順・判断基準・図であって、著者の文章そのものではない
- 言い回しが要点になる箇所（対句、定義文、節を締める箴言）は引用として残す
- 成果物を出力先に置き、作業データを `.jv/` に隔離する
- `.gitignore` で文字起こし・成果物・`.assets` を除外している
- この README にも生成物の実例を載せていない

## 必要なもの

- [Claude Code](https://claude.com/claude-code)
- [uv](https://docs.astral.sh/uv/)
- Python 3.12（uv が用意する。バージョンの明示は必須 — 理由は[設計上の判断](#設計上の判断)）

Python の依存は実行時に uv が解決するので、事前のインストールは要らない。ffmpeg は `imageio-ffmpeg` が持つものを実行時に解決する。**バイナリは同梱していない。**

音声を含まないソース（Web記事・X投稿のみ）であれば、標準の Python だけで動く。

## インストール

スキルディレクトリに置く。

```bash
git clone https://github.com/Helicon1968/japanese-verbatim ~/.claude/skills/japanese-verbatim
```

Windows（PowerShell）:

```powershell
git clone https://github.com/Helicon1968/japanese-verbatim "$env:USERPROFILE\.claude\skills\japanese-verbatim"
```

### 更新

新しい版を取るときは pull する。

```bash
cd ~/.claude/skills/japanese-verbatim && git pull
```

```powershell
cd "$env:USERPROFILE\.claude\skills\japanese-verbatim"; git pull
```

辞書（`glossary/terms.json`）に自分で語を足していると、pull が衝突することがある。
その場合は手元の変更を退避してから取り込み、必要な語を足し直す。

```bash
git stash && git pull && git stash pop
```

特定の版に固定したいときは、`git tag` で一覧を見てから切り替える。

```bash
git tag && git checkout <タグ>
```

## 使い方

Claude Code のセッションで、変換したいソースを指定して呼ぶ。

```
https://example.com/article を japanese-verbatim で日本語化して
```

```
video.mp4 を japanese-verbatim で日本語化して
```

引数なしで呼ばれた場合、スキルはカレントフォルダを推測で解析しない。何を変換するか・どこに出力するか・成果物の名前・どの版を作るかを確認してから始める。

### 処理の流れ

```
0.入力確定 ─▶ 取得 ─▶ 文字起こし ─▶ [ゲート1] ─▶ 用語辞書 ─▶ 文書化 ─▶ [ゲート2･3･4] ─▶ 付録 ─▶ 後始末
 (確認)              (キャッシュ)                                              (検証結果を同梱)
                          │                                   │
                          └──── RED なら設定を直して再実行 ────┘
```

### 作業領域

出力先の直下に置いてよいのは成果物だけ。中間ファイルは `.jv/` に隔離する。

```
<出力先>/
  <名前>.md               成果物
  <名前>.exempt.txt       忠実性チェックの判断記録
  <名前>.assets/          出典から取り込んだ画像・動画の切り抜き
  .jv/
    work/                 中間ファイル（finish で消える）
    audit/                出典の生データ・検証結果（後から再検証するため残す）
    cache/                再実行キャッシュ
```

`workspace.py status` は出力先に残った非成果物を報告する。報告が出たら規約違反。

## 4つのゲート

終了コードは **0 = GREEN / 1 = RED / 2 = 検証不能**。

**2 を合格として扱わない。** 検証できないことは合格ではない。

| | 見るもの | 主な検査 |
|---|---|---|
| **ゲート1** | 文字起こし | カバレッジ、発話レベルのギャップ（音量の実測で判定）、30秒窓の境界に揃った欠落、反復ループ |
| **ゲート2** | 成果物の構造 | 三層構成、出典の明記、図の帰属、目次、Mermaid構文、罫線文字による自作図、出典画像の取りこぼし |
| **ゲート3** | 忠実性 | 原文訳ブロックのラテン文字トークンが出典に存在するか |
| **ゲート4** | 文体 | 訳者の記述に混ざった敬体、原文訳で1文だけ孤立した常体 |

ゲート3が検査できるのは固有名詞・識別子の出所だけで、日本語の訳出が忠実かどうかは判定できない。ただし捏造がもっとも危険なのはそこなので、そこだけは機械で見る。

指摘された語のうち正当な正規化（発話 "control X" → `Ctrl+X` など）は `<名前>.exempt.txt` に理由つきで記録する。コマンドラインの一時的なフラグに逃がさない。判断を残しておけば後から見直せる。

## 設計上の判断

ここに書いてあるのは、いずれも実測の結果そうなったもの。根拠と手順は [`references/asr-playbook.md`](references/asr-playbook.md) にある。

### 文字起こしの既定設定を使わない

62.5分の英語講演を faster-whisper の既定設定で文字起こししたところ、**内容の39%が消えていた。**

| | 語数 | 文字化された長さ |
|---|---|---|
| 既定設定 | 6,916 | 58.7分 |
| 推奨設定 | 11,346 | 62.5分 |

6箇所・計3.8分が丸ごと欠落していたが、出力されたテキストは自然な日本語として読めてしまう。欠落区間の平均音量は −14.7 dB で、通常の発話区間（−14.6 dB）と同等だった。**沈黙ではなく、明瞭な発話が消えていた。**

原因は `vad_filter` と `condition_on_previous_text` の既定値にある。ゲート1は、この種の静かな欠落を検出して止めるために作った。

### hotwords を事前に渡さない

技術用語の精度を上げる目的で `hotwords` を渡すのは、実測の結果やめた。

同じ講演を、同じモデル・同じ設定で hotwords だけ変えて2回回した結果:

| | hotwords あり（79語） | hotwords なし |
|---|---|---|
| 反復ループ | **5箇所** | **0件** |
| 語数 | 11,039 | 11,401 |
| ギャップの判定 | 発話が消えている | 2件ともすべて沈黙 |

hotwords に渡した語にモデルが引っ張られてループに入り、その間の発話が丸ごと消える。欠落は約440語で、節の結論がまるごと含まれていた。

もっとも危険なのは、**このときゲート1が1箇所しか検出せず、GREEN で通した**ことだった。残り4箇所は目視で見つけた。

さらに、hotwords は用語辞書から自動生成されるため、辞書が育つほど悪化する。誤認識を辞書に戻すほど語数が増え、ループの機会も増える。

辞書は事後の置換にだけ使い、事前には効かせない。

### 精度はモデルサイズでは稼げない

`small` を `medium` に上げても、欠落の問題は解決しない（欠落は設定起因であってモデルサイズ起因ではない）。実測では両モデルとも同じ固有名詞を誤認識し、3倍の時間に見合わなかった。

技術用語の精度は、事後の辞書置換と、画面に映った文字との照合で稼ぐ。

なお、焼き込み字幕も自動生成であることが多く、音声と同じ誤りを繰り返すだけで独立した確認にならない。**字幕を正解として扱わない。**

### `--python 3.12` の明示は必須

省略すると uv が別の Python を選び、tokenizers のホイールが見つからずソースビルドに落ちて失敗する。エラーは `pyproject.toml` の TOML パースエラーとして出るため、原因が分かりにくい。

### ffmpeg のパスを固定しない

uv のキャッシュパスはハッシュを含む。固定すると環境が変わった時点で壊れる。毎回 `imageio_ffmpeg.get_ffmpeg_exe()` で解決する。

## 既知の制約

- 実測値は1台・1素材のもの（Xeon E3-1245 v2 / 4コア8スレッド / GPU併用なし、62.5分の英語講演）。hotwords に関する結論も同じ素材から導いている。傾向としては再現すると考えているが、環境や素材によって数値は変わる
- GPU なしの環境では 62分の音声に約55分かかる。速度は設定によって3倍以上変わるため、モデル名だけで速度を語れない
- **ゲート1は反復ループを取りこぼす**（上記の実例で5箇所中1箇所しか検出しなかった）。ゲートは目視の代わりではなく、目視すべき箇所の当たりをつけるもの
- ゲート3はラテン文字のトークンしか照合できない。日本語の訳出が忠実かどうかは人間が読むしかない
- ソースが最初から日本語の場合、原文訳の契約が成立しない。要点抽出・構成分析・記述検証のいずれを作るかを確認する運用にしている
- 検証はすべて Windows + PowerShell 環境で行っている。macOS / Linux でも動くはずだが未検証

## 構成

```
SKILL.md                      手順と規約の本体
references/
  asr-playbook.md             文字起こしの設定と既知の失敗モード5種（実測付き）
glossary/
  terms.json                  技術用語の誤認識辞書
scripts/
  workspace.py                作業領域の作成・点検・後始末
  transcribe.py               文字起こし（キャッシュ・速度ベンチ付き）
  verify_transcript.py        ゲート1：文字起こしの品質
  verify_doc.py               ゲート2：成果物の構造
  verify_fidelity.py          ゲート3：原文訳の識別子の出所
  verify_style.py             ゲート4：文体の一貫性
  glossary.py                 用語辞書の適用・追加・集計
  grab_frames.py              画面変化のフレーム抽出
  contact_sheet.py            候補フレームの一覧表（選別用）
  fetch_images.py             出典画像の取得
  make_appendix.py            精度に関する付録の生成
tests/
  test_glossary.py            辞書の置換（行またぎの回帰を含む）
  test_workspace.py           後始末（掴まれたディレクトリの回帰を含む）
```

テストは枠組みを使わない。`python tests/test_glossary.py` のように直接走らせる。
どちらも**2回以上再現した不具合の回帰**を残したものである。

## 報告と連絡

不具合・改善案は Issue へ。とくに次の2つは手元の環境だけでは確かめられないので、報告があると助かる。

- macOS / Linux での動作（未検証）
- GPU ありの環境での実行時間

用語辞書に足したい誤認識があれば、誤りと正しい表記の対応を添えて Issue に書いてほしい。素材そのもの（音声・文字起こし・訳文）は添付しないこと。
