# 文字起こしの設定と既知の失敗モード

## 基本の実行形

```bash
uv run --no-project --python 3.12 --with faster-whisper python transcribe.py
```

`--python 3.12` の明示は必須。省略すると uv が別の Python を選び、
tokenizers のホイールが見つからずソースビルドに落ちて失敗する
（エラーは `pyproject.toml` の TOML パースエラーとして出るため原因が分かりにくい）。

ffmpeg は `imageio_ffmpeg.get_ffmpeg_exe()` で毎回解決する。
uv のキャッシュパスはハッシュを含むため、固定すると環境が変わった時点で壊れる。

## 推奨設定

```python
segs, info = model.transcribe(
    "audio.wav",
    language="en",
    beam_size=5,
    hotwords=None,                   # ← 既定で渡さない。理由は失敗モード3
    vad_filter=False,                # ← 既定 True は発話を丸ごと落とす
    condition_on_previous_text=False,# ← 既定 True は文脈崩壊で窓をスキップする
    no_speech_threshold=0.9,         # ← 既定 0.6 は無音判定が厳しすぎる
    compression_ratio_threshold=2.8,
)
```

**hotwords は既定で渡さない。** 語の精度を上げる一方で反復ループを誘発し、
内容を丸ごと落とすことがある（失敗モード3）。用語は事後の `glossary.py apply` と
画面照合で回復する。`transcribe.py` は辞書から hotwords を自動注入するので、
`--no-hotwords` で切る。

```bash
python transcribe.py video.mp4 --model small --beam 5 --no-hotwords
```

hotwords の有無はキャッシュ鍵に入る（無しのとき `.nohw` が付く）。
2パスを突き合わせるときに同じ箱を共有して上書きされることはない。

音声の前処理は 16kHz モノラル。

```bash
ffmpeg -nostdin -i input.mp4 -vn -ac 1 -ar 16000 -c:a pcm_s16le -y audio.wav
```

## モデル選択

**推測せず、3分の断片で実測してから決める。** モデルを大きくしても、
欠落の問題は解決しない（欠落は設定起因であってモデルサイズ起因ではない）。

参考実測値（Xeon E3-1245 v2 / 4コア8スレッド / GPU併用なし）。
**設定によって3倍以上変わるため、モデル名だけで速度を語らないこと。**

| モデル | 設定 | 速度 | 62.5分の音声 |
|---|---|---|---|
| `small` | beam=1, vad_filter=True | 2.11倍速 | 約30分 |
| `medium` | beam=1, vad_filter=True | 0.71倍速 | 約88分 |
| `small` | **beam=5, vad_filter=False（推奨設定）** | 0.67〜1.1倍速 | **実測 約55分** |

推奨設定が遅いのは当然で、beam を広げ、無音区間も含めて全体を処理しているため。
**速度と引き換えに欠落を防いでいる。**

`transcribe.py --bench` は推奨設定と同じパラメータで測るので、見積りは本実行と
比較可能。ただし3分の断片で測るため、その区間の発話密度によって上下する
（実例: ベンチは0.67倍速＝93分と見積もったが、実際は55分で完了した）。
**見積りは上限として扱う。**

`medium` の精度向上はこのケースでは僅かで（両モデルとも同じ固有名詞を誤認識）、
3倍の時間に見合わなかった。**技術用語の精度はモデルサイズでは稼げない。
事後の辞書置換と画面との照合で稼ぐ。**

かつてここには「hotwords で稼ぐのが費用対効果が高い」と書いてあったが、
**実測でこれは誤りだった**（失敗モード3）。hotwords は個々の語を当てにいく一方で
ループを誘発し、落とした分量のほうが大きい。事前に効かせるのではなく、
事後に `glossary.py apply` で直す。

## 失敗モードと対処

### 1. 発話の脱落（カバレッジ不足）

**症状**: ゲートが「発話レベルのギャップ」を検出する。ギャップ長が30秒の整数倍。

**原因**: `vad_filter=True` が発話区間を無音と誤判定するか、
`condition_on_previous_text=True` で文脈が崩壊し、窓ごと出力が空になる。

**対処**: 上記の推奨設定で再実行する。

**実例**: 62.5分の講演で、既定設定では58.7分しか文字化されず、
6箇所・計3.8分が脱落した。語数は 6,916 → 11,346 に増えた（**39%の取りこぼし**）。
ギャップ区間の平均音量は −14.7dB で、通常発話区間（−14.6dB）と同等だった。

**重要**: ギャップの存在だけでは沈黙と区別がつかない。音量の実測が判定の根拠になる。

### 2. 反復ハルシネーション

**症状**: 同一フレーズが連続して10回以上繰り返される。

**原因**: 話者が実際に反復した箇所や、口ごもり・無音区間でモデルがループに入る。

**対処**: **再実行では直らない。** 該当箇所を特定し、繰り返しを1回に整理して訳出する。
処理したら `--repetition warn` でゲートを通す。

**注意**: 話者が意図的に反復している場合もある（例: 指示の書き方を揶揄して
「これをしろ、これをしろ」と繰り返す）。文脈を見て、削るか残すか判断する。

### 3. hotwords が誘発する反復ループ

**症状**: 失敗モード2と同じ反復ループが出る。ただし原因が音声側ではなく**設定側**にある。

**原因**: `hotwords` に渡した語にモデルが引っ張られ、その近辺でループに入る。
ループが窓を食いつぶすため、**その間の発話が出力から丸ごと消える**。

**対処**: `--no-hotwords` で回す。用語は事後に `glossary.py apply` で直す。
失敗モード2と違い、**これは再実行で直る**（設定を変えるのだから当然である）。

**実例**: 62.5分の同じ講演を、同じモデル・同じ設定で hotwords だけ変えて2回回した。

| | hotwords あり（79語） | hotwords なし |
|---|---|---|
| ループ | **5箇所** | **0件** |
| カバレッジ | — | 97.4% |
| 語数 | 11,039 | 11,401 |
| ギャップの判定 | 発話が消えている | 2件ともすべて沈黙 |

欠落は約440語。消えた中には、節の主題の転換を述べた結論の一文が
まるごと含まれていた。該当箇所（30:52）の実測音量は −15.1 dB で、
発話区間の基準（−15.0 dB）と同等 — **沈黙ではなく、明瞭な発話が消えていた**。

**もっとも危険な点**: このときゲート1は**1箇所しか検出せず、GREEN で通した**。
残り4箇所は目視で見つけた。ゲートが通ったことは内容が揃っている証明にならない。

**辞書が育つほど悪化する。** hotwords は `glossary.py` の辞書から自動生成されるため、
誤認識を辞書に戻すほど語数が増え、ループの機会も増える。この講演では
置換27件の時点より62件の時点のほうが条件が悪かった。
**辞書は事後置換のためだけに使い、事前には効かせない。**

### 4. 技術用語の誤認識

**症状**: `CLAUDE.md` が "CloudMD"、`pull request` が "pool request" になる。

**対処**:
1. `glossary.py apply` で既知の誤りを置換（**事後**。hotwords として事前に
   渡してはならない — 失敗モード3）
2. **画面のあるソースでは、該当時刻のフレームを抽出して照合する**
   これがもっとも確実。スクリーンキャストではコマンド名・ファイルパスが
   画面に表示されているため、音声より信頼できる
3. 新しく見つけた誤りを `glossary.py add` で辞書に追加する

**実例**: 62.5分の講演で事後置換が効いたのは49種・のべ150箇所ほど。
`Claude` 系の誤認識（`Cloud Code` 38件、`Cloud MD` / `CloudMD` / `clotmd` など）が
大半を占める。事前に hotwords を渡さなくても、この規模は事後で回収できる。

### 5. セグメントが極端に長い

**症状**: 5分あたり8〜11セグメントしかない（1セグメント30〜60秒）。

**意味**: 句読点による分割が効いていない。内容欠落の前兆であることが多い。
カバレッジと併せて確認する。正常時は5分あたり60〜90セグメント程度。

## 画面付きソースでの補強

スクリーンキャストや講演動画では、音声だけに頼らない。

```bash
FF=$(python -c "import imageio_ffmpeg; print(imageio_ffmpeg.get_ffmpeg_exe())")
"$FF" -nostdin -loglevel error -ss 1800 -i video.mp4 -frames:v 1 \
      -vf scale=1280:-1 -y frame_1800.jpg
```

抽出したフレームを読み、コマンド名・ファイルパス・設定値を確認する。
**音声で曖昧だった技術用語は、ほぼ必ず画面に映っている。**

焼き込み字幕がある場合、その字幕自体も自動生成であることが多く、
同種の誤りを含む。**字幕を正解として扱わないこと。**

実例（いずれも同じ講演の焼き込み字幕）:

| 字幕の表示 | 実際 |
|---|---|
| `CLOUD CODE` | Claude Code |
| `THE ASIAN SDK` | the Agent SDK |
| `SETTINGS JASON` | settings.json |
| `VERSEL SKILL THING` | Vercel の skills の件 |

字幕は音声と同じ誤りを繰り返すだけで、独立した確認にならない。
**独立した根拠になるのは画面に映った文字のほう**（ターミナルの出力、
エディタのファイル、ドキュメントの表）である。
